\section{ARQUITETURA DE SOFTWARE E TECNOLOGIAS}

A implementação da plataforma WeFIND envolveu a escolha de tecnologias para o desenvolvimento da aplicação móvel, o armazenamento dos dados e a comunicação entre os serviços. Como ensinam Pressman e Maxim (2021) e Valente (2023), a arquitetura de software de um sistema móvel deve conciliar produtividade no ciclo de desenvolvimento, baixo acoplamento entre camadas e robustez na persistência e distribuição dos dados em nuvem.

O projeto adotou o padrão arquitetural cliente-servidor distribuído, segmentado em duas camadas independentes: a camada cliente móvel (executada nos smartphones dos usuários) e a camada de serviços em nuvem (hospedada na infraestrutura do Supabase e na plataforma Render). Essa abordagem desacoplada assegura que a lógica de interface e renderização gráfica ocorra localmente no processador do celular, ao passo que as operações de autenticação, persistência relacional, armazenamento de arquivos multimídia, mensageria externa e sincronização em tempo real são delegadas a serviços gerenciados em nuvem (BaaS, modelo de infraestrutura de retaguarda em nuvem).

A consistência dos dados e a segurança das operações são garantidas pela integração com o banco de dados relacional PostgreSQL, estruturado com políticas de segurança em nível de linha (RLS). Esse mecanismo transfere o controle de acesso e isolamento de permissões para o próprio motor do banco de dados, impedindo que requisições não autorizadas alterem ou excluam dados alheios, mesmo em eventuais falhas na camada de apresentação móvel.

Este capítulo detalha as decisões técnicas e as ferramentas que compõem a arquitetura do WeFIND, descreve a infraestrutura de computação em nuvem provida pelo Supabase e pelo gateway de mensageria da Evolution API, apresenta a modelagem lógica relacional das entidades e tabelas no PostgreSQL e documenta as ferramentas auxiliares empregadas no projeto.

A biblioteca React Native foi adotada como núcleo para a interface móvel, operando em estreita integração com o React. Foram utilizados React Native 0.81.5, React 19.1.0 e Expo SDK 54 (pacote \textit{expo} 54.0.29). O código da aplicação foi desenvolvido em JavaScript com JSX, conforme os arquivos-fonte do projeto (React, 2026; React Native, 2026; Expo, 2026). A decisão por essa tecnologia fundamentou-se em critérios técnicos de produtividade e desempenho perante outras alternativas de desenvolvimento móvel:

Em relação ao desenvolvimento puramente nativo (como construir separadamente uma aplicação em Kotlin para Android e outra em Swift para iOS), a abordagem isolada exigiria a manutenção de duas bases de código distintas. Para este projeto individual, o React Native permitiu desenvolver para as plataformas móveis a partir de uma base de código compartilhada em JavaScript e JSX.

Frente a tecnologias baseadas em navegadores embutidos (como aplicações web convencionais ou plataformas baseadas em navegadores embutidos via \textit{WebView}), o React Native compila para os componentes de interface nativos do sistema operacional. Essa abordagem favorece o desempenho gráfico na renderização de mapas com múltiplos marcadores e na resposta aos eventos de toque, além de facilitar a comunicação com os sensores do dispositivo.

Em conjunto com o React Native, utilizou-se a plataforma Expo. O Expo foi escolhido por fornecer um conjunto de módulos nativos pré-configurados, reduzindo a necessidade de configurações manuais em ferramentas específicas de cada sistema operacional. No WeFIND, a integração com o aparelho apoiou-se em pacotes do Expo: \textit{expo-location} 19.0.8 para consultar os serviços de localização disponíveis no dispositivo, incluindo o GPS quando habilitado; \textit{expo-image-picker} 17.0.10 para acesso à câmera e à galeria; e \textit{expo-image-manipulator} 14.0.8 para comprimir fotos no dispositivo antes do envio. A precisão das coordenadas pode variar conforme o aparelho, as permissões concedidas e as condições de recepção (Expo, 2026).

A camada cartográfica baseia-se em \textit{react-native-maps} 1.20.1, responsável pela renderização dos mapas do Google Maps e Apple Maps e pela exibição de marcadores. Para gerar os cartazes com código QR, empregou-se \textit{react-native-view-shot} 4.0.3, que captura a interface como imagem, junto ao módulo \textit{expo-sharing} 14.0.8 para abrir o compartilhamento nativo. A navegação entre telas utiliza \textit{@react-navigation/native} 7.1.25. A estilização visual adotou NativeWind 4.2.1, baseado em Tailwind CSS 3.4.19 (React Native Maps, 2026; React Native View Shot, 2026; Expo, 2026; React Navigation, 2026; NativeWind, 2026; Tailwind CSS, 2026).

No Android, a visualização cartográfica utiliza o provedor Google Maps por meio da configuração da chave da Google Maps Platform, enquanto a biblioteca \textit{react-native-maps} fornece a integração da interface nativa com o React Native. A aplicação também pode abrir o Google Maps por meio de uma URL externa para apresentar a localização de uma publicação ou orientar o usuário até o ponto indicado. O funcionamento desses recursos depende da disponibilidade de conexão, da concessão da permissão de localização e da configuração válida da chave para o aplicativo (GOOGLE MAPS PLATFORM, 2026; REACT NATIVE MAPS, 2026).

Para proteger o tráfego de rede e a integridade das consultas, foram inseridas regras de validação no próprio aplicativo cliente. Os formulários executam verificações em tempo real sobre campos de preenchimento obrigatório, validam a consistência sintática de endereços de e-mail e realizam a formatação padronizada de números telefônicos antes do envio à nuvem.

\subsection{Serviços em Nuvem, Segurança e Mensageria}

Para organizar a descrição da infraestrutura, esta subseção apresenta os serviços em nuvem, os mecanismos de proteção e a integração de mensageria. O modelo de dados e o ciclo de vida das publicações são tratados separadamente, nas subseções seguintes.

Na camada de serviços em nuvem, adotou-se a plataforma Supabase (SUPABASE, 2026), utilizando a biblioteca cliente \textit{@supabase/supabase-js} 2.87.3. A versão do serviço Supabase e do PostgreSQL gerenciado é administrada pela própria plataforma. A escolha do Supabase, em vez do Google Firebase ou de um backend próprio desenvolvido do zero, baseou-se em dois fatores principais:

O Supabase Auth também intermedeia a autenticação social com o Google. Nesse fluxo, o aplicativo solicita ao Supabase uma URL de autenticação, abre o navegador do dispositivo para que o usuário conclua o login na conta Google e, após o retorno por um esquema de redirecionamento próprio do aplicativo, troca o código recebido por uma sessão autenticada. Dessa forma, o WeFIND não coleta nem armazena a senha da conta Google; a autenticação é realizada pelo provedor externo e a sessão resultante é gerenciada pelo Supabase Auth (SUPABASE, 2026).

Em comparação ao Firebase, que utiliza banco de dados NoSQL orientado a documentos, o Supabase utiliza o banco relacional PostgreSQL. No WeFIND, informações sobre animais, tutores, publicações e avistamentos exigem relações diretas e integridade referencial. Bancos NoSQL tornariam essas consultas complexas e gerariam duplicação de dados. Além disso, o Supabase oferece suporte nativo a políticas de segurança em nível de linha, assegurando que cada usuário acesse e altere apenas os seus próprios registros.

Em relação à criação de um backend próprio (como uma API em Node.js com banco manual), o Supabase eliminou a necessidade de configurar servidores dedicados, certificados e rotinas manuais de manutenção. A plataforma fornece, de forma integrada, autenticação de usuários (Supabase Auth), banco de dados relacional (PostgreSQL), armazenamento de imagens na nuvem (Supabase Storage) e comunicação em tempo real para o chat e alertas.

No que se refere à segurança, o WeFIND distribui os mecanismos de proteção entre o aplicativo móvel, as funções de borda e o banco de dados. As comunicações com o Supabase e com os serviços externos utilizam endereços HTTPS. O login com o Google emprega o fluxo OAuth com PKCE, enquanto o tratamento das senhas é delegado ao Supabase Auth, sem armazenamento ou implementação de hashes de senha no aplicativo. No banco de dados, as políticas de segurança em nível de linha (RLS) restringem as operações de acordo com o usuário autenticado e com as permissões administrativas definidas para cada tabela.

As funções de borda concentram as operações que exigem credenciais de provedores externos. Dessa forma, a chave da Evolution API é mantida como variável de ambiente no servidor e não é incluída no aplicativo móvel. A função de mensageria exige uma sessão autenticada para receber solicitações de envio e devolve ao cliente somente o resultado necessário da operação, sem repassar o corpo da resposta do provedor.

Os códigos temporários utilizados no cadastro, na recuperação de senha e na alteração do telefone são gerados por uma fonte criptograficamente segura. No armazenamento, esses códigos são representados por resumos SHA-256, possuem prazo de validade e são removidos após o uso. O fluxo também limita a cinco tentativas de validação e aplica intervalo mínimo entre novas solicitações. Como medida complementar, os registros de log foram ajustados para não expor códigos, senhas, chaves, telefones completos ou respostas sensíveis de serviços externos.

Backups, restauração, expiração global de sessões e disponibilidade da infraestrutura dependem de configurações operacionais dos provedores Supabase e Render. Por esse motivo, esses aspectos não são apresentados como garantias fornecidas exclusivamente pelo aplicativo.

Para viabilizar a comunicação com o WhatsApp, utilizou-se a Evolution API (EVOLUTION API, 2026), hospedada na plataforma em nuvem Render (RENDER, 2026). A decisão por essa ferramenta em vez de APIs corporativas oficiais, como Meta Cloud API ou Twilio, considerou o escopo acadêmico e comunitário do projeto, além dos custos e dos procedimentos de configuração envolvidos nessas alternativas. Como solução de código aberto conectada por requisições HTTP REST, a Evolution API permitiu realizar, no ambiente utilizado, o envio de códigos para recuperação de senha e de avisos quando um animal é avistado sem cobrança por mensagem pela biblioteca. Os custos e a disponibilidade da hospedagem e da infraestrutura externa, contudo, dependem dos respectivos provedores.

A tabela \textit{usuarios} centraliza os dados cadastrais dos participantes do sistema. O campo identificador primário conecta-se diretamente à chave única fornecida pelo serviço Supabase Auth, registrando o nome, endereço de e-mail, fotografia de perfil, número de telefone para contato emergencial, cidade, estado de residência e o registro de data e hora de criação da conta.

A tabela \textit{animais} gerencia os animais domésticos cadastrados preventivamente pelos tutores, registrando nome, espécie, raça, porte físico, coloração da pelagem, sexo, idade aproximada, código de microchip eletrônico, código QR exclusivo para a coleira de identificação e URL da foto de perfil para emissão da carteirinha digital.

A tabela \textit{publicacoes} armazena os anúncios georreferenciados cadastrados pela comunidade, classificados como Perdido, Encontrado ou Adoção. Cada registro está vinculado ao usuário autor e pode possuir uma chave estrangeira para a tabela \textit{animais} (\textit{pet\_id}), viabilizando alertas automáticos sem redigitação de dados. A tabela armazena título, descrição, coordenadas de latitude e longitude em ponto flutuante, endereço, data do fato, indicador de resolução, carimbo de criação (\textit{created\_at}), data da última renovação (\textit{updated\_at}) e data limite para expiração ativa (\textit{data\_expiracao}).

A tabela \textit{fotos\_publicacoes} gerencia a galeria de imagens vinculada a cada anúncio, mantendo cardinalidade um-para-muitos com a tabela \textit{publicacoes} e armazenando a URL pública da mídia persistida no armazenamento em nuvem do Supabase Storage.

A tabela \textit{avistamentos} organiza os relatos colaborativos fornecidos pela comunidade ao visualizarem animais soltos na via pública. Cada registro conecta-se à respectiva publicação e ao usuário informante, registrando as coordenadas de latitude e longitude do ponto do avistamento, referências descritivas, fotografia de evidência e carimbo temporal.

A tabela \textit{mensagens} dá suporte ao canal de comunicação privativo da aplicação. Ela reúne o identificador da publicação em discussão, o usuário remetente, o destinatário, o conteúdo textual da mensagem, anexo opcional de imagem, indicador booleano de confirmação de leitura e registro cronológico do envio.

Complementarmente, a persistência dá suporte às entidades de colaboração comunitária: a tabela de voluntários de acolhimento (\textit{foster\_volunteers}) registra os membros dispostos a atuar como lar temporário, suas preferências de espécies e especificações da moradia; por sua vez, o serviço de pontuação e ranking (\textit{ranking.js}) agrega dinamicamente no cliente e na nuvem os registros da semana corrente, atribuindo pontuações (10 pontos por publicação, 25 pontos por lar temporário ativo e 60 pontos por reencontro confirmado) e aplicando pseudonimização no nome dos membros (exibindo apenas o primeiro nome e a inicial do sobrenome) para preservar a privacidade perante a LGPD.

A segurança e a integridade do banco de dados relacional são asseguradas por políticas de segurança em nível de linha. Por meio desse mecanismo, implementado diretamente no mecanismo do PostgreSQL, define-se que qualquer usuário autenticado ou visitante possui permissão de leitura sobre as publicações de animais ativos, porém apenas o usuário proprietário daquele registro detém privilégios para alterar ou excluir suas próprias publicações e dados de perfil, impedindo modificações não autorizadas.

\subsection{Ciclo de Vida das Publicações e Política de Limpeza}

Para solucionar a permanência de postagens antigas nas redes sociais, nas quais animais já resgatados continuam sendo compartilhados por meses, o WeFIND adota uma lógica ativa de controle do ciclo de vida das publicações.

Cada anúncio possui um período de 30 dias de vigência ativa, contado a partir do cadastro ou da última renovação. Três dias antes do vencimento, o aplicativo envia um aviso para que o responsável possa renovar a publicação. Caso a busca prossiga, a prorrogação é realizada com um toque no botão ``Renovar'' no painel de gestão. Sem a renovação, a publicação fica inativa e deixa de aparecer no mural e no mapa público, mas ainda pode ser renovada durante o período de carência de 30 dias.

Após o período de carência, a publicação pode ser removida permanentemente pela rotina de limpeza acionada pelo aplicativo durante o carregamento do mural, com intervalo mínimo de uma hora entre verificações na mesma execução do aplicativo. No fluxo de limpeza local, são considerados os anúncios do usuário autenticado. A exclusão remove também os registros de fotos relacionados e os arquivos correspondentes no Supabase Storage. Assim, a regra prevê uma vigência de 30 dias e, sem renovação, uma janela adicional de 30 dias antes da remoção definitiva, quando a rotina de limpeza for executada.

\subsection{Motor Heurístico de Correspondência Multicritério}

A localização de um animal doméstico depende da agilidade com que informações complementares são conectadas. Em redes sociais e canais informais, os usuários precisam revisar manualmente dezenas de postagens para tentar reconhecer seu animal em fotografias divulgadas por terceiros. Para automatizar essa verificação, o WeFIND incorpora o módulo de correspondência automática, que realiza o cruzamento sistemático entre publicações ativas de tipos complementares (animais Perdidos e animais Encontrados).

O motor opera em duas etapas sequenciais: a triagem eliminatória imediata e o cômputo ponderado de similaridade morfológica e espacial. Seu resultado é uma sugestão de correspondência entre publicações; o motor não registra automaticamente um avistamento nem altera a localização de uma publicação.

\subsubsection{Critérios de Eliminação Imediata}

Para reduzir o envio de alertas pouco relevantes, o algoritmo executa previamente uma checagem de viabilidade biológica e física. Três critérios funcionam como filtros eliminatórios imediatos: caso qualquer um deles seja violado, o sistema atribui escore nulo (0 pontos), encerrando o cálculo sem necessidade de avaliações adicionais.

O primeiro critério corresponde à incompatibilidade de espécies, em que registros pertencentes a categorias zoológicas distintas (como cão e gato, ou equino e ave) são descartados sumariamente. O segundo critério avalia a divergência de sexo comprovado, invalidando a equivalência quando ambos os anúncios informam com certeza o gênero do animal e estes divergem formalmente entre macho e fêmea. Por fim, o terceiro critério trata dos portes físicos antagônicos, considerando mutuamente exclusivos os casos em que um animal classificado nos extremos inferiores da escala (porte mini ou pequeno) é confrontado com outro registrado nos limites superiores (porte grande ou gigante).

\subsubsection{Sistema de Ponderação, Penalidades e Proximidade por Haversine}

Ultrapassada a barreira dos critérios eliminatórios, os anúncios são submetidos a uma matriz de pontuação cumulativa projetada para produzir um escore heurístico entre 0 e 100 pontos. Cada atributo físico coincidente adiciona valor ao índice de compatibilidade, ao passo que divergências relevantes em raça, pelagem ou distância geográfica aplicam penalidades. Esses pesos constituem uma decisão de projeto e ainda não representam uma probabilidade estatística calibrada. \subsubsection{Classificação Semântica e Disparo Automatizado de Notificações}

O total de pontos obtido é convertido em um índice heurístico de compatibilidade apresentado em uma escala de 0\% a 100\%. Essa escala é utilizada apenas para ordenar e comunicar o grau relativo de semelhança entre os registros; não representa a probabilidade estatística de que os dois anúncios correspondam ao mesmo animal.

A faixa de compatibilidade muito alta, com índices iguais ou superiores a 85\%, sinaliza convergência em vários atributos físicos e proximidade geográfica. A faixa de compatibilidade alta, situada entre 70\% e 84\%, indica um conjunto relevante de características coincidentes. A faixa de compatibilidade possível, compreendida entre 60\% e 69\%, recomenda conferência manual dos registros. Escores inferiores a 60\% não atingem o limiar definido para notificação automática.

Sempre que uma nova publicação atinge compatibilidade de no mínimo 60\% com algum animal ativo no banco de dados, o WeFIND aciona a rotina \textit{processAndNotifyPetMatches}. Esse serviço registra a sugestão e pode notificar ambas as partes envolvidas por meio da central interna, de alertas nativos e, quando o serviço externo estiver configurado e disponível, de mensagens no WhatsApp via Evolution API. A confirmação da identidade e eventual atualização de localização pertencem a fluxos posteriores e dependem de ação humana.

\subsubsection{Distinção entre Correspondência Automática e Registro de Avistamento}

A correspondência automática e o registro de avistamento utilizam informações semelhantes, mas possuem finalidades e efeitos distintos. A correspondência automática compara duas publicações ativas de status oposto, Perdido e Encontrado, para identificar uma possível relação entre o animal perdido por um usuário e o animal encontrado por outro. Seu produto é um escore heurístico e uma notificação, sem alteração automática das publicações.

O registro de avistamento parte de uma publicação já existente e acrescenta um novo relato sobre o animal observado em outro momento ou local. Depois que o informante confirma que o animal visualizado corresponde à publicação sugerida, o serviço de avistamentos grava o relato na tabela correspondente, atualiza a localização mais recente da publicação principal e preserva os registros anteriores para compor a linha do tempo. Portanto, a correspondência automática auxilia a descoberta de possíveis correspondências, enquanto o avistamento confirmado atualiza o acompanhamento espacial da publicação.
