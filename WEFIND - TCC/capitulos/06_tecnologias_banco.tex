\section{ARQUITETURA DE SOFTWARE E TECNOLOGIAS}

Os capítulos anteriores descrevem o que o WeFIND faz; falta mostrar sobre quais componentes essas funções se apoiam. Um aplicativo que depende de localização, fotos, mensagens em tempo real e avisos por WhatsApp precisa dividir responsabilidades entre o dispositivo, serviços em nuvem e provedores externos. Essa divisão é o objeto do projeto arquitetural, que Pressman e Maxim (2021) tratam como uma etapa própria, anterior ao projeto dos componentes.

Para apoiar a comunicação dessas decisões, a ISO/IEC/IEEE 42010:2022 estabelece requisitos para estruturar e expressar descrições de arquitetura, incluindo pontos de vista e modelos, e distingue a arquitetura da descrição que a representa (ISO, 2022).

A biblioteca React Native foi adotada como núcleo para a interface móvel, em integração com o React. Foram utilizados React Native 0.81.5, React 19.1.0 e Expo SDK 54 (pacote \textit{expo} 54.0.29). O código da aplicação foi desenvolvido em JavaScript com JSX (React, 2026; React Native, 2026; Expo, 2026).

Em relação ao desenvolvimento puramente nativo (como construir separadamente uma aplicação em Kotlin para Android e outra em Swift para iOS), a abordagem isolada exigiria a manutenção de duas bases de código distintas. Para este projeto individual, o React Native permitiu desenvolver para as plataformas móveis a partir de uma base de código compartilhada em JavaScript e JSX.

Em relação a soluções baseadas em \textit{WebView}, o React Native permite compor a interface com componentes nativos e integrar recursos do dispositivo por meio de módulos.

Em conjunto com o React Native, utilizou-se a plataforma Expo e seus módulos: \textit{expo-location} 19.0.8 para consultar os serviços de localização disponíveis no dispositivo; \textit{expo-image-picker} 17.0.10 para acesso à câmera e à galeria; e \textit{expo-image-manipulator} 14.0.8 para comprimir fotos antes do envio. A precisão das coordenadas depende do aparelho, das permissões concedidas e das condições de recepção (Expo, 2026).

A camada cartográfica baseia-se em \textit{react-native-maps} 1.20.1, responsável pela renderização dos mapas do Google Maps e Apple Maps e pela exibição de marcadores. Para gerar os cartazes com código QR, empregou-se \textit{react-native-view-shot} 4.0.3, que captura a interface como imagem, junto ao módulo \textit{expo-sharing} 14.0.8 para abrir o compartilhamento nativo. A navegação entre telas utiliza \textit{@react-navigation/native} 7.1.25. A estilização visual adotou NativeWind 4.2.1, baseado em Tailwind CSS 3.4.19 (React Native Maps, 2026; React Native View Shot, 2026; Expo, 2026; React Navigation, 2026; NativeWind, 2026; Tailwind CSS, 2026).

No Android, a visualização cartográfica utiliza o provedor Google Maps por meio da configuração da chave da Google Maps Platform, enquanto a biblioteca \textit{react-native-maps} integra o mapa à interface. A aplicação também pode abrir o Google Maps por meio de uma URL externa para apresentar a localização de uma publicação ou orientar o usuário até o ponto indicado. O funcionamento depende da conexão, das permissões de localização e da configuração válida da chave (Google Maps Platform, 2026; React Native Maps, 2026).

Os formulários também validam campos obrigatórios, verificam a sintaxe de endereços de e-mail e formatam números telefônicos antes do envio. Essas verificações no cliente complementam os controles aplicados nos serviços de backend.

ChatGPT e GitHub Copilot foram empregados como ferramentas auxiliares de programação e produção de conteúdo (OpenAI, 2026; GitHub, 2026). \subsection{Serviços em Nuvem, Segurança e Mensageria}

O backend utiliza a plataforma Supabase (Supabase, 2026) e a biblioteca cliente \textit{@supabase/supabase-js} 2.87.3. O Supabase reúne os serviços de autenticação, banco de dados PostgreSQL, armazenamento de arquivos e atualização em tempo real empregados pelo aplicativo; a versão dos serviços gerenciados é administrada pela plataforma. Essa composição foi escolhida para atender às necessidades do projeto sem desenvolver e manter todos esses componentes separadamente.

O Supabase Auth também intermedeia a autenticação social com o Google. Nesse fluxo, o aplicativo solicita ao Supabase uma URL de autenticação, abre o navegador do dispositivo para que o usuário conclua o login na conta Google e, após o retorno por um esquema de redirecionamento próprio do aplicativo, troca o código recebido por uma sessão autenticada. Dessa forma, o WeFIND não coleta nem armazena a senha da conta Google; a autenticação é realizada pelo provedor externo e a sessão resultante é gerenciada pelo Supabase Auth (Supabase, 2026). Esse fluxo segue o padrão OAuth com PKCE.

Para este projeto, o PostgreSQL foi selecionado por oferecer um modelo relacional adequado às relações entre perfis, publicações, imagens, avistamentos e conversas.

O Supabase também foi preferido a implementar e operar, no escopo do projeto, serviços próprios para autenticação, persistência e armazenamento. Essa decisão reduz a quantidade de infraestrutura que precisa ser administrada diretamente no projeto, mas não elimina a dependência das configurações e da disponibilidade do provedor.

As políticas de segurança em nível de linha (RLS) são configuradas no banco, com regras específicas para cada tabela. No esquema consultado, a leitura anônima de dados de perfis, publicações e avistamentos foi restringida; as regras de avistamentos e conversas também limitam o acesso conforme autenticação e participação.

As funções de borda concentram operações que usam credenciais de provedores externos. A chave da Evolution API é mantida como variável de ambiente no servidor, fora do aplicativo móvel; a função de mensageria exige uma sessão autenticada para receber solicitações de envio.

Os códigos temporários de cadastro, recuperação de senha e alteração de telefone são representados no armazenamento por resumos SHA-256, possuem prazo de validade e são removidos após o uso. O fluxo limita as tentativas de validação e aplica intervalo mínimo entre novas solicitações. Os registros de log também foram ajustados para evitar a exposição de credenciais e dados sensíveis.

Backups, restauração, expiração global de sessões e disponibilidade dependem das configurações e dos serviços dos provedores Supabase e Render; não são garantias fornecidas exclusivamente pelo aplicativo.

Para a comunicação com o WhatsApp, utilizou-se a Evolution API (Evolution API, 2026), hospedada no Render (Render, 2026). No ambiente utilizado, a integração por requisições HTTP REST apoiou o envio dos códigos de verificação de cadastro e de recuperação de senha e dos avisos do sistema, como novos avistamentos e possíveis correspondências entre publicações, para os usuários que autorizaram esse canal.

    \includegraphics[width=\textwidth,height=0.78\textheight,keepaspectratio]{imagens/02_modelagem/figura09_modelo_logico_banco_v3.png}

A Figura~\ref{fig:modelo_logico_banco} reúne as tabelas que sustentam os fluxos centrais do aplicativo, com os nomes adotados no banco de dados: \textit{profiles}, \textit{items}, \textit{item\_photos}, \textit{sightings}, \textit{conversations}, \textit{messages}, \textit{notifications}, \textit{reports}, \textit{rewards} e \textit{item\_claims}. As chaves primárias (PK) e estrangeiras (FK) estão destacadas, e as linhas indicam relacionamentos de um para muitos: o traço marca o lado ``um'' e o pé de galinha, o lado ``muitos''. Tabelas auxiliares, como a de códigos temporários de verificação, e as de recursos complementares não integram esse recorte.

A tabela \textit{profiles} armazena os dados cadastrais dos usuários. Seu identificador corresponde ao identificador da conta criada no Supabase Auth, e os demais campos registram nome, e-mail, número de WhatsApp, foto de perfil, cidade, estado, a indicação de perfil administrador e a preferência por receber avisos pelo WhatsApp.

A tabela \textit{items} concentra as publicações de animais perdidos e encontrados. Cada registro está vinculado ao usuário responsável (\textit{owner\_id}) e reúne título, descrição, categoria, situação, características do animal (espécie, raça, porte, sexo, cor e idade), endereço, bairro, cidade, estado, coordenadas geográficas, data do ocorrido, indicação de encerramento (\textit{resolved}) e prazo de expiração (\textit{expires\_at}). As fotografias ficam em \textit{item\_photos}, que guarda o endereço de cada arquivo enviado ao Supabase Storage.

A tabela \textit{sightings} registra os avistamentos, associando cada relato à publicação e ao usuário informante, com local, descrição, foto e data. A comunicação privada é organizada em \textit{conversations}, que vincula dois participantes a uma publicação e registra se a conversa está ativa ou encerrada, e em \textit{messages}, que guarda remetente, destinatário, conteúdo, eventual foto, estado de leitura e data de envio de cada mensagem.

Por fim, \textit{notifications} armazena os avisos de cada usuário, com tipo, título, mensagem, publicação relacionada e indicação de leitura; \textit{reports} registra as denúncias, com motivo, detalhes, situação e o administrador responsável pela análise; \textit{rewards} guarda a recompensa opcional oferecida em uma publicação, com valor, moeda, descrição e situação; e \textit{item\_claims} registra as solicitações de devolução com comprovação de tutela, associando a publicação e o solicitante ao relato, à fotografia enviada, à situação do pedido e ao eventual motivo de recusa.

As publicações têm vigência ativa de 30 dias, contados a partir do cadastro ou da última renovação. Três dias antes do vencimento, o aplicativo pode enviar um aviso para que o responsável renove o anúncio. Sem renovação, a publicação fica inativa e deixa de aparecer no mural e no mapa público, mas ainda pode ser renovada durante o período adicional de 30 dias.

Após o período de carência, a publicação pode ser removida permanentemente pela rotina de limpeza acionada durante o carregamento do mural, com intervalo mínimo de uma hora entre verificações na mesma execução do aplicativo. No fluxo de limpeza local, são considerados somente os anúncios do usuário autenticado, e a exclusão também remove os registros das fotos relacionadas e os arquivos correspondentes no Supabase Storage. Portanto, o sistema não executa uma varredura global: a remoção definitiva das publicações de cada conta depende da execução da rotina no contexto dessa conta.

\subsection{Algoritmo Heurístico de Correspondência}

O WeFIND compara publicações não resolvidas de animais perdidos e encontrados para sugerir possíveis correspondências. Antes de calcular a pontuação, a rotina descarta pares com espécies incompatíveis, sexo informado como oposto ou porte classificado nos extremos pequeno e grande/gigante. Para os demais pares, soma bônus e penalidades definidos para atributos do animal e proximidade geográfica, calculada pela fórmula de Haversine quando há coordenadas. O resultado é um índice heurístico entre 0 e 100, limitado nessa faixa e arredondado; não representa uma probabilidade estatística de reencontro. O sistema apresenta correspondências com pontuação mínima de 55 pontos na busca padrão. Já a rotina de notificações aplica o limiar de 60 pontos e processa até três resultados por publicação. A diferença entre os limites permite exibir sugestões que ainda não acionam notificações automáticas. A pontuação, portanto, serve como critério de ordenação e triagem, não como confirmação de identidade. As faixas de distância com GPS e os demais pesos foram definidos de forma empírica durante o desenvolvimento, sem calibração com casos reais. A atribuição das maiores pontuações às menores distâncias é coerente com os achados de Huang et al. (2018), segundo os quais 75\% dos gatos perdidos foram localizados a até 500 metros do ponto de desaparecimento; contudo, esse estudo trata apenas de gatos e não determina os valores específicos adotados no WeFIND.

Com a definição da arquitetura de software, a modelagem do banco de dados e as ferramentas de desenvolvimento estabelecidas, o Capítulo~7 apresenta o projeto de interface do WeFIND, detalhando os aspectos de usabilidade, a identidade visual e as telas desenvolvidas.
